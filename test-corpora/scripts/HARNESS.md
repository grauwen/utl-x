# Harness & per-profile baseline (`harness.py`)

Phase 0a (the runner) + Phase 0b (the baseline) of the `%utlx 1.1` build plan
(`docs/architecture/utlx-1_1-build-plan.md`). Pairs with the policy spec
(`docs/architecture/parser-strictness-profiles.md`) and the test doctrine
(`docs/architecture/utlx-test-corpora.md` §5.7).

## What it measures

For each input under `corpora/`, the harness probes the **current parser** with an
identity transform (`%utlx 1.0 / input <fmt> / output <fmt> / --- / $input`) via the utlx CLI and
records **accept / reject / error(timeout|crash)**. It then compares that against each profile's
expected verdict in `expectations/profiles/<profile>/parse-verdicts.yaml`.

> **Baseline semantics — read this.** The `lenient | standard | strict` profiles are **not yet
> implemented** in the parsers (they're the design in `parser-strictness-profiles.md`). So this run
> compares **one current, un-profiled parser** against **each profile's spec**. The per-profile
> **mismatches are the Phase-0c hardening backlog** — e.g. `strict` wants a trailing comma
> *rejected* but today's parser *accepts* it. Mismatches here are **expected**, not test failures.

`error` (timeout / crash / OOM) never satisfies an expectation — a reject-via-crash is still a
robustness problem and is counted separately.

## Run it

```bash
./gradlew :modules:cli:jar          # the probe needs a built CLI
pip3 install pyyaml                  # once

python3 test-corpora/scripts/harness.py                 # all profiles, summary
python3 test-corpora/scripts/harness.py --profile strict -v
python3 test-corpora/scripts/harness.py --json test-corpora/baseline.json
# custom CLI (e.g. the engine jar, or a native build):
python3 test-corpora/scripts/harness.py --cli "java -jar modules/cli/build/libs/cli-1.3.0.jar"
```

## How a case is defined

Inputs and oracles are **separated** (the scaffold's design):

- **input** — a file under `corpora/<class>/<format>/` (`conformance`, `malformed`, `security`, …).
- **oracle** — an entry in `expectations/profiles/<profile>/parse-verdicts.yaml`:
  ```yaml
  - input: corpora/malformed/json/trailing_comma.json
    verdict: reject        # or accept
    reason: trailing-comma # the §4 dimension
  ```

The same input carries a **different expected verdict per profile** — that is the spec↔conformance
link to `parser-strictness-profiles.md` §4. Add a profile by adding
`expectations/profiles/<name>/parse-verdicts.yaml`; the harness auto-discovers it.

## Format detection — by path/oracle, not by extension

Several UTL-X formats **share a file extension** — `odata`, `jsch`, `osch` are `.json`; `xsd`, `tsch`
are `.xml` — so the extension can't say *which* parser to use. `resolve_format()` picks the format
most-explicit-first:

1. an explicit `format:` on the oracle case (wins — use for anything ambiguous);
2. the **format directory** in the corpus path `corpora/<class>/<format>/<file>` (so
   `corpora/conformance/odata/valid_entity.json` → `odata`, **not** `json`);
3. the file extension (fallback only).

So OData-JSON lives at `corpora/conformance/odata/*.json` and is parsed as `odata`; a plain JSON file
under `.../json/*.json` is parsed as `json`. The probe serialises to **json** to isolate the *parse*
step (we measure input acceptance, not the serializer round-trip).

## Seed corpus (current)

Covers the §4 matrix dimensions, JSON-first + one XML security case:

| input | dimension | strict | lenient |
|---|---|---|---|
| `conformance/json/valid_object.json` | well-formed | accept | accept |
| `malformed/json/trailing_comma.json` | trailing comma | reject | accept |
| `malformed/json/block_comment.json` | comment | reject | accept |
| `malformed/json/duplicate_key.json` | duplicate key | reject | accept (last-wins) |
| `malformed/json/unquoted_key.json` | unquoted key | reject | accept |
| `malformed/json/leading_bom.json` | BOM | reject | accept (strip) |
| `malformed/json/control_char.json` | control char in string | reject | accept |
| `security/xml/doctype_entity.xml` | DOCTYPE / entity (XXE) | reject | **reject** (floor) |

`leading_bom.json`, `control_char.json`, and `tab_indent.yaml` contain raw bytes and are generated by
`make-byte-seeds.sh` (text editors mangle them).

Also seeded beyond the table: XML/CSV/YAML malformed cases (`mismatched_tag`, `undefined_entity`,
`ragged_rows`, `unclosed_quote`, yaml `duplicate_key`) and OData-JSON valids — **19 inputs × 3 profiles**.

## Scope / next

- Accept/reject only so far. Roundtrip-fidelity and cross-format oracles
  (`cross-format/…/canonical.udm.json`) and the resource-bounds checks (`expectations/bounds.yaml`)
  are the next harness capabilities.
- Profiles seeded: **`strict`, `standard`, `lenient`** — the full §4 triad.
- Formats covered: JSON, XML, CSV, YAML, and **OData-JSON** (valid conformance). Still uncovered:
  the schema formats (`jsch`/`xsd`/`osch`/`tsch`) and binary (`avro`/`protobuf`) — the next tranche,
  now that path-based format detection supports them.
