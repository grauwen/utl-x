# WB02: the Go client panics on import — it cannot be used at all

> **WB = wrapper bug** (`wrappers/*` — the first-party client libraries that drive the engine).
> This is **WB02**.

**Status:** **FIXED** (2026-11-11) by regenerating the bindings. Root cause identified
arithmetically before regenerating — see *Root cause*.
**Priority:** **Critical for Go users.** The package cannot be imported, so the client is not
usable in any form — there is no partial functionality to fall back on.
**Component:** `wrappers/go/utlxclient` — `proto/utlxe/v1/utlxe.pb.go` (generated).
**Found by:** attempting to run the Go tests for
[WB01](WB01-dotnet-wrapper-writes-frame-bytes-out-of-order.md).

> **One-line:** the generated protobuf descriptor is rejected by the protobuf-go runtime, so the
> package's `init()` panics and any program that imports the client dies at startup.

## Reproduction

A program whose only content is a blank import is enough:

```go
package main

import (
	"fmt"
	_ "github.com/grauwen/utl-x/wrappers/go/utlxclient"
)

func main() { fmt.Println("imported the client successfully") }
```

```
panic: runtime error: slice bounds out of range [-5:]

google.golang.org/protobuf/internal/filedesc.(*File).unmarshalSeedOptions(...)
  .../protobuf@v1.36.11/internal/filedesc/desc_init.go:262
google.golang.org/protobuf/internal/filedesc.(*File).unmarshalSeed(...)
github.com/grauwen/utl-x/wrappers/go/utlxclient/proto/utlxe/v1.file_utlxe_v1_utlxe_proto_init()
  .../proto/utlxe/v1/utlxe.pb.go:2596
```

The message never prints. `go test ./...` fails the same way, before any test body runs.

## Root cause: a find-and-replace rewrote bytes inside a binary descriptor

The namespace rename `org.apache.utlx` → `com.glomidco.utlx` was applied globally, and it reached the
**embedded binary descriptor** inside the generated `.pb.go`. The string was replaced; the length
prefixes that describe it were not.

The tail of the raw descriptor read:

```
… HealthResponse  B ,  \n \x1c com.glomidco.utlx.engine.proto  B \n UtlxeProto P \x01 b \x06 proto3
                  │ │     │
                  │ │     └── field 1 (java_package), length 0x1c = 28
                  │ └──────── options submessage length 0x2C = 44
                  └────────── field 8 (options), wire type 2
```

The arithmetic is decisive:

| | bytes |
|---|---|
| length prefix says | **28** |
| `com.glomidco.utlx.engine.proto` actually is | **30** |
| `org.apache.utlx.engine.proto` is | **28** ← exactly what the prefix was written for |

The parser read 28 bytes where 30 sat, so every following field offset was shifted by two, and the
cascade surfaced as `slice bounds out of range [-5:]` in `unmarshalSeedOptions`. The enclosing
options length was wrong by the same two bytes (44, should be 46).

Regenerating produced exactly those two corrections — `B,` → `B.` (44 → 46) and `\x1c` → `\x1e`
(28 → 30) — which confirms the diagnosis rather than merely replacing the file.

**It was the only affected file.** A repo-wide scan for generated files carrying both an embedded
descriptor and the new namespace found one: this one.

## What is *not* the cause

`go build ./...` and `go vet ./...` both pass. The failure is at **run time**, in the generated
file's `init()`, while the runtime parses the embedded raw descriptor — so compilation proves
nothing here, which is worth knowing before trusting a green build.

The obvious hypothesis was a generator/runtime version skew:

```
generated by: protoc-gen-go v1.36.6, protoc v5.29.3
resolved:     google.golang.org/protobuf v1.36.11
```

**It was tested and it is not the cause.** Pinning the runtime down to the generator's own version
(`go get google.golang.org/protobuf@v1.36.6`) reproduces the identical panic, so this is not a skew
that a `go.mod` constraint fixes. The dependency change was reverted rather than left in place as a
speculative edit.

`slice bounds out of range [-5:]` while unmarshalling the *seed options* points at the embedded
descriptor bytes in `utlxe.pb.go` being malformed — truncated, hand-edited, or produced from a
`.proto` using a feature the pinned runtime cannot read. Determining which needs the `.proto` source
and a regeneration, which is why this report stops at the diagnosis.

## The fix

Regenerated from `proto/utlxe/v1/utlxe.proto` with the **same versions the file was originally
produced with** — `protoc 29.3` (v5.29.3) and `protoc-gen-go v1.36.6` — so the only differences are
the ones listed below:

```
protoc -I proto \
  --go_out=<out> \
  --go_opt=module=github.com/grauwen/utl-x/wrappers/go/utlxclient/proto \
  --go_opt=Mutlxe/v1/utlxe.proto=github.com/grauwen/utl-x/wrappers/go/utlxclient/proto/utlxe/v1 \
  proto/utlxe/v1/utlxe.proto
```

The `.proto` carries no `option go_package`, hence the `M` mapping; worth adding one so the command
is reproducible without remembering the flag.

### The regeneration also fixed a staleness nobody had noticed

The committed bindings predate `ErrorCode_HEAP_PRESSURE = 11` (EF15/EB02, heap backpressure). A Go
client could not have recognised that error code — it was simply absent from the enum. That is the
second thing a dead test suite hides: not only did the client not work, it had silently fallen
behind the protocol.

## What this was hiding: twelve dead integration tests

The Go package has a real integration suite that **spawns the engine and speaks the stdio protobuf
protocol** — `TestHealth`, `TestLoadTransformation`, `TestExecute`, `TestExecuteBatch`,
`TestExecutePipeline`, `TestCopyStrategy25Messages`, `TestFullLifecycle` and five more, about 2.5
seconds each.

**Every one of them has been unrunnable since the rename**, because the package panicked before any
test body could execute. They all pass now:

```
ok  github.com/grauwen/utl-x/wrappers/go/utlxclient  30.441s
```

That is the real cost of this bug. Not only was the Go client unusable — the only end-to-end
coverage of the stdio protocol from a client's side was silently switched off, and the repository
reported nothing, because `go build` and `go vet` both pass on a file whose descriptor is corrupt.

### Recommended guard

Nothing in CI runs the Go tests. At minimum, a smoke test that imports the package and constructs a
message would have caught this the day it broke:

```go
func TestPackageImportsAndProtoInitialises(t *testing.T) {
    _ = &pb.StdioEnvelope{Type: pb.MessageType_HEALTH_CHECK}
}
```

But the twelve integration tests are the greater loss, and the real fix is a CI job that runs
`go test ./...` for the wrapper. A build-only check cannot catch this class of fault — as this bug
demonstrates for two years of generated-code history.

## The lesson worth keeping

**A global find-and-replace must not cross a generated file containing binary data.** The namespace
rename was correct everywhere else; it was wrong here only because the bytes it rewrote were inside
a length-prefixed structure. Generated files should be regenerated after a rename, not edited by
it — and ideally excluded from repo-wide replacements altogether.
